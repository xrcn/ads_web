# GFast 3.3.12 前端选择性升级设计

## 1. 目标与状态边界

将 `GFast授权版3.3.12.zip` 中相对当前前端基版的有效框架修复合并到 `ads_web`，保留 ADS 已有页面、接口契约、品牌、环境配置和微信业务前端。

完成状态限定为 `LOCAL_VERIFIED`。本任务不执行 commit、push、生产发布或已有页面批量改造。

## 2. 当前基线

- 仓库：`E:\ads\ads_web`。
- Branch：`develop`。
- 基线 HEAD：`8558a6854ef71a7970854c0c4d54562b8858fd55`。
- 启动扫描时工作树 clean，领先 `origin/develop` 5 个 commit。
- ZIP 内上游有效范围：`a41fa93` 至 `9847c88`。
- 前端 `package.json` 与 ZIP 一致，没有依赖版本升级。

branch、HEAD 或 dirty 状态变化后，本设计的三方分类失效，实施前必须重新扫描。

## 3. 合入范围

- 合入 `uploadFile`、`uploadImg` 的受控状态同步，避免 computed 副作用和递归更新。
- 保留 ADS 已有上传配置读取逻辑；只移植上游稳定性修复，不整文件覆盖。
- 合入图片类型、大小、数量校验和单图/多图回显修复。
- 合入 401 并发单弹窗；请求发出后 Token 已刷新时重试原请求。
- 合入 Element Plus 暗色卡片与消息提示背景修复。
- 当前已删除的 ORF 示例页面保持不变。

## 4. 明确排除

- 不修改前端依赖版本，不引入测试框架或其他新增依赖。
- 不覆盖 `.env`、`.env.production`、API 地址、WebSocket 地址和品牌内容。
- 不修改微信 callback、麦序、模板、调度、报备、统计、主播档案及可视化控制台页面。
- 不批量修改或重新生成已有业务页面。

## 5. 合并方法

1. 使用上游前后版本与 ADS 当前 HEAD 做三方对比。
2. 当前已包含的 ORF 示例删除不重复修改。
3. 上传组件按行为逐项移植，保留 ADS 现有配置接口和 props 契约。
4. 401 与主题样式按最小 patch 合入，不改通用请求成功/错误响应契约。
5. 使用现有静态验证能力和构建验证，不引入新依赖。

## 6. 交互与错误处理

- `modelValue` 变化时使用深比较同步展示副本，避免父子组件更新回路。
- 图片类型、大小或数量超限时前端拒绝文件并显示现有风格错误消息，不发送上传请求。
- 上传成功后从临时列表移除对应项并追加服务端返回项；删除和预览继续同步父组件值。
- 多个并发请求返回 401 时只显示一个重新登录窗口。
- 请求发出时的 Token 与当前 Token 不同，说明 Token 已刷新，只重试该请求一次。
- 暗色卡片和消息提示使用 Element Plus 标准背景变量。

## 7. 验证设计

- 使用现有静态验证方式检查 401 单弹窗、Token 变化重试、上传受控状态、图片类型和大小校验。
- 执行 `npm run build`。
- 本地页面检查登录、单图、多图、文件上传、初始化回显、删除、预览及暗色消息提示。
- 检查用户/角色页面未因公共请求层变化产生回归。
- 运行 `git diff --check` 并重新审计 tracked/untracked 边界。

## 8. 风险与回滚

- 公共上传组件影响多个后台页面，必须验证单图、多图、附件、初始化回显、删除和重复文件名边界。
- 401 请求重试必须限制在 Token 已变化的场景，避免失效 Token 无限重试。
- 本地 build 不证明生产静态资源、登录态或接口行为；未经授权不得发布。
- 修改未 commit 前，如验证失败，使用精确 inverse patch 回退本批文件；不得使用 `git reset --hard` 或 `git checkout --`。

## 9. 完成标准

- 计划内前端修复全部合入，排除项未进入 diff。
- 静态验证和 `npm run build` 通过。
- 关键本地交互通过，或明确列为未验证项。
- diff check 与 dirty 边界审计通过。
- 最终状态为 `LOCAL_VERIFIED`；Git 未提交，生产未发布。

预计实施与验证耗时 0.5–1.5 小时；若本地登录环境不可用，报告 `PARTIAL`，不以构建通过代替交互验证。
